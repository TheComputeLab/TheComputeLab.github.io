## What is an AI Experiment?

An AI experiment is a controlled test designed to answer a specific
question about an AI system.

Instead of simply building an application and observing whether it works,
an experiment defines what we want to learn, establishes a setup, changes
one or more variables, measures the result and documents the conclusion.

<div class="ai-experiment-definition">

<span>EXPERIMENT MODEL</span>

<strong>QUESTION → HYPOTHESIS → SETUP → RUN → MEASURE → ANALYZE → CONCLUDE</strong>

<small>
The goal is not always to prove that something works. A useful experiment
can also demonstrate why an approach fails.
</small>

</div>


## Why Experimentation Matters

AI systems can behave differently when we change the model, prompt,
context, retrieval strategy, temperature, hardware, dataset or system
architecture.

Experimentation helps separate assumptions from measurable evidence.

<div class="ai-experiment-card-grid">

<div>
<strong>UNDERSTAND</strong>
<p>Learn how a model or system behaves.</p>
</div>

<div>
<strong>COMPARE</strong>
<p>Compare models, prompts, architectures or configurations.</p>
</div>

<div>
<strong>OPTIMIZE</strong>
<p>Improve quality, latency, memory usage or cost.</p>
</div>

<div>
<strong>DEBUG</strong>
<p>Identify why an AI workflow produces unexpected results.</p>
</div>

<div>
<strong>VALIDATE</strong>
<p>Test whether an idea works before investing in a full application.</p>
</div>

<div>
<strong>LEARN</strong>
<p>Convert experiments and failures into reusable engineering knowledge.</p>
</div>

</div>

<div class="ai-experiment-lifecycle">

## Writing a Good Hypothesis

A hypothesis should describe an expected relationship that can be tested.

For example:

> Increasing retrieval quality should improve the factual accuracy of
> answers generated by a RAG application.

A useful hypothesis identifies what is being changed and what outcome is
expected.

<div class="ai-experiment-hypothesis">

<div>
<span>VARIABLE</span>
<strong>Retrieval strategy</strong>
</div>

<div>→</div>

<div>
<span>EXPECTED EFFECT</span>
<strong>Better context</strong>
</div>

<div>→</div>

<div class="highlight">
<span>MEASURE</span>
<strong>Answer quality</strong>
</div>

</div>


## Designing a Controlled Experiment

Whenever possible, change one important variable at a time.

For example, when comparing two prompts:

<div class="ai-experiment-control-flow">

<div>

<small>Same</small>
</div>

<div>+</div>

<div>
<strong>DATASET</strong>
<small>Same</small>
</div>

<div>+</div>

<div>
<strong>SETTINGS</strong>
<small>Same</small>
</div>

<div>+</div>

<div class="highlight">
<strong>PROMPT</strong>
<small>Changed</small>
</div>

<div>→</div>

<div>
<strong>RESULT</strong>
<small>Compare</small>
</div>

</div>

This makes it easier to attribute an observed difference to the variable
being tested.


## Model Experiments

Model experiments can compare:

- Different model families
- Different model sizes
- Hosted and local models
- Quantized and unquantized models
- General-purpose and task-specific models
- Different context lengths
- Different inference settings

Useful measurements include:

- Response quality
- Accuracy
- Latency
- Throughput
- Token usage
- Memory consumption
- GPU utilization
- Cost
- Reliability


## Prompt Experiments

Prompt experiments test how instructions and context affect model output.

Possible variables include:

- System instructions
- Few-shot examples
- Output format
- Role definitions
- Context ordering
- Explicit constraints
- Reasoning instructions
- Retrieved context
- Structured output requirements

A useful comparison keeps the model and input dataset constant while
changing the prompt.


## RAG Experiments

RAG experiments can investigate the complete retrieval pipeline.

<div>→</div>
<div>EMBEDDINGS</div>
<div>→</div>

<div>CONTEXT</div>
<div>→</div>
<div>LLM</div>
<div>→</div>
<div>ANSWER</div>

Useful questions include:

- Does smaller chunking improve retrieval?
- Does overlap improve recall?
- Which embedding model works better?
- Does hybrid search outperform vector-only search?
- How many retrieved chunks should be supplied?
- Does reranking improve answer quality?
- How often does the system retrieve irrelevant context?

## Embedding Experiments

Embeddings represent information as vectors that can be compared using
similarity measures.

Experiments can compare:

- Embedding models
- Chunk sizes
- Chunk overlap
- Similarity functions
- Metadata filtering
- Vector database settings
- Top-k retrieval values

The key question is whether the embedding and retrieval configuration
returns useful context for the intended task.

## Local AI Experiments

Local AI makes it possible to investigate model behavior directly on
controlled hardware.

Possible experiments include:

- CPU vs GPU inference
- Different GPUs
- Different quantization formats
- Model size vs VRAM usage
- Context length vs memory
- Batch size vs throughput
- Temperature and output behavior
- Local model serving
- Containerized inference

These experiments are especially useful when designing systems that need
privacy, offline operation or predictable infrastructure costs.


## Benchmarking AI Systems

Benchmarking means measuring a system using a repeatable procedure.

A benchmark should define:

1. The workload
2. The hardware or runtime
3. The model and version
4. The configuration
5. The dataset
6. The metrics
7. The measurement method
8. The number of runs
9. The results
10. The conclusion

Avoid comparing numbers obtained from substantially different setups
without documenting those differences.

A/B testing compares two alternatives under similar conditions.

Example:

<div class="ai-experiment-ab">

<strong>Prompt A</strong>
<small>Baseline</small>
</div>

<div>VS</div>

<div class="highlight">
<span>VERSION B</span>
<strong>Prompt B</strong>
<small>Candidate</small>
</div>

</div>

Both versions should ideally receive the same evaluation dataset and be
measured using the same criteria.


## Failure Analysis

A failed experiment is still useful if the failure is understood.

When a system fails, investigate:

- What input caused the failure?
- What did the model receive?
- What context was retrieved?
- Which tool was selected?
- What output was generated?
- Which constraint was violated?
- Was the failure deterministic?
- Can the failure be reproduced?
- What change might prevent it?


## Reproducibility

A useful experiment should be reproducible.

Record:

- Code version
- Model name and version
- Prompt
- Dataset
- Configuration
- Hardware
- Software versions
- Random seeds where relevant
- Runtime settings
- Experiment date
- Results

Without this information, it can be difficult to determine why a result
changed later.

## Example Python Experiment

A simple experiment can compare two configurations over the same inputs.

<pre class="ai-experiment-code"><code>results = []

for test_case in dataset:

    # Run the baseline configuration
    baseline = run_model(
        model=model,
        prompt=prompt_a,
        input=test_case
    )

    # Run the candidate configuration
    candidate = run_model(
        model=model,
        prompt=prompt_b,
        input=test_case
    )

    # Measure both outputs using the same evaluation method
    baseline_score = evaluate(baseline, test_case)
    candidate_score = evaluate(candidate, test_case)

    results.append({
        "baseline": baseline_score,
        "candidate": candidate_score
    })

# Analyze the collected results
report = summarize_results(results)

print(report)</code></pre>

The important part is not the exact Python implementation. The important
principle is that both configurations are tested against the same
evaluation process.


## Documenting Results

A good experiment report should answer:

### Question

What were we trying to learn?

### Hypothesis

What did we expect to happen?

### Setup

What model, data, hardware and configuration were used?

### Variables

What changed between the baseline and the experiment?

### Measurements

Which metrics were collected?

### Results

What did the measurements show?

### Analysis

Why might the result have occurred?

### Conclusion

Was the hypothesis supported?

### Next Experiment

What should be tested next?

## Common Experiment Mistakes

Avoid these common problems:

- Changing several variables simultaneously
- Comparing different datasets
- Using inconsistent evaluation criteria
- Reporting only the best result
- Ignoring failed runs
- Not recording model versions
- Not recording prompts
- Testing too few examples
- Optimizing a metric that does not represent the real goal
- Comparing hardware without documenting configuration

during technical interviews.

Be prepared to explain:

- How would you compare two LLMs?
- How would you evaluate a RAG system?
- How would you investigate a poor retrieval result?
- How would you measure inference latency?
- How would you benchmark a local model?
- How would you compare quantized and unquantized models?
- How would you design an A/B test for prompts?
- How would you make an AI experiment reproducible?
- How would you move a successful experiment into production?
- How would you balance quality, latency and cost?
